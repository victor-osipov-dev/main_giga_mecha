# VOXEL ARCADE RS — RUST MVP MASTER PLAN

## 1. Роль и задача

Ты — ведущий Rust-разработчик, архитектор сетевых игровых серверов и специалист по Minecraft Java Edition Protocol.

Твоя задача — создать Voxel Arcade RS: минималистичное высокопроизводительное Minecraft-совместимое серверное ядро полностью на Rust.

Проект должен принимать подключения обычных официальных Minecraft Java-клиентов без модификаций.

В дальнейшем на ядре будут работать произвольные игры: Flappy Bird, Snake, Pong, Terraria-like, платформеры, гонки и другие.

**На этапе MVP главная задача — корректная работа протокола, мультиплеера и минимальной игровой платформы.**

Не реализуй Vanilla Survival, генерацию обычного Minecraft-мира, мобов, крафт, редстоун и прочие механики, если они не нужны для подключения клиента.

### Обязательные требования

- Rust Stable.
- Один самостоятельный серверный процесс.
- Без JVM и обязательного Java-прокси.
- Minecraft Java 26.3 — первая нативная версия.
- Возможность добавлять другие протоколы.
- Приоритет последних и распространённых версий.
- Корректная серверная авторизация.
- Настоящий мультиплеер.
- Отсутствие обязательных клиентских модов.
- Минимальное потребление памяти.
- Модульная архитектура.
- Надёжная обработка ошибок.
- Автоматические тесты.
- Готовность к будущему Game Runtime.

### Целевой бюджет памяти

- До 50 MiB RSS в простое — желаемый результат.
- До 100 MiB RSS при 20 подключённых игроках в простом игровом мире — целевой результат.
- Измерять также пиковый RSS и потребление контейнера.

Цифры являются инженерными целями, а не гарантией.

Если для корректности протокола или безопасности необходимо больше памяти, сохрани функциональность и документируй причину превышения.

# 2. Правила автономной разработки

1. Не придумывай существующие функции сторонних библиотек.
2. Проверяй актуальные исходники и документацию.
3. Не копируй код без проверки лицензии.
4. Не реализуй пакеты на основе неподтверждённых предположений.
5. Не смешивай игровые действия и обработку Minecraft-пакетов.
6. Не создавай ненужную многопоточность.
7. Не используй `unsafe` без доказанной необходимости.
8. Не отключай online-mode ради упрощения публичного сервера.
9. Не заявляй о совместимости без реального тестирования.
10. После каждого этапа собирай проект и запускай тесты.
11. Не удаляй работающий функционал без необходимости.
12. Используй точные версии зависимостей и Cargo.lock.
13. Документируй архитектурные решения.
14. Работай последовательно, небольшими завершёнными изменениями.

Автономно выполняй задачи, не требующие внешних секретов и пользовательских действий. Не публикуй сервер или релиз от имени владельца без разрешения.

Выбери между двумя подходами:

**A. Использовать подходящую существующую Rust-библиотеку протокола.**

**B. Реализовать собственный минимальный протокольный слой, переиспользуя проверенные форматы и генераторы данных.**

Предпочитай A, если библиотека поддерживается, достаточно легковесна и действительно предоставляет необходимые серверные возможности.

Не создавай новый универсальный Minecraft-протокол с нуля только ради независимости от стороннего кода.

# 5. ЭТАП 2 — Minecraft Network Transport

Цель — реализовать корректный сетевой транспорт Minecraft Java.

### TCP Server

Реализуй:

- Прослушивание порта 25565.
- Асинхронное принятие соединений.
- Ограничение активных соединений.
- Контролируемое завершение.
- Таймауты.
- Корректную отмену задач.
- Ограниченные очереди отправки.
- Защиту от медленных клиентов.

### Packet Codec

Поддержи:

- Minecraft VarInt.
- Minecraft VarLong.
- Big-endian primitive types.
- UTF-8 strings.
- UUID.
- Packet length framing.
- Packet ID.
- NBT для требуемых пакетов.
- Compression.
- Encryption, необходимое для online-mode.
- Полное и частичное чтение TCP-пакетов.

Реализуй проверки:

- Максимального размера пакета.
- Максимальной длины строки.
- Максимальной вложенности NBT.
- Переполнений VarInt.
- Отрицательных и некорректных длин.
- Лимитов распакованного объёма.
- Некорректной последовательности состояний.

### Тесты

Используй unit tests, property tests и fuzzing там, где это практически оправдано.

Проверь fragmented TCP reads и ситуацию, когда в одном TCP read приходит несколько Minecraft-пакетов.

Критерий готовности: пакетный codec правильно обрабатывает проверенные тестовые векторы и не падает от повреждённых входных данных.

# 6. ЭТАП 3 — Поддержка Minecraft Java 26.3

Первая целевая версия:

Minecraft Java 26.3, Protocol 777.

Не используй packet ID или registry data от других версий.

### State Machine

Реализуй:

1. Handshaking.
2. Status.
3. Login.
4. Configuration.
5. Play.

У каждого соединения должен быть явно определённый state.

Пакет, недопустимый в текущем состоянии, должен приводить к контролируемой обработке ошибки.

### Status State

Поддержи:

- Server List Ping.
- MOTD.
- Версию сервера.
- Максимальное количество игроков.
- Текущее количество игроков.
- Ping/Pong.

### Login State

Поддержи:

- Login Start.
- Проверку имени и идентификаторов в рамках протокола.
- Login Encryption для online-mode.
- Проверку сессии Minecraft.
- Login Success.
- Обязательные подтверждения.
- Compression, если включено.

### Configuration State

Поддержи все обязательные для Protocol 777 действия:

- Client Information.
- Registry Data.
- Known Packs.
- Configuration Acknowledgements.
- Finish Configuration.
- Переход в Play.

Точный состав пакетов и их направления проверяй по схеме 26.3, а не по старым версиям Minecraft.

### Play State

Минимально реализуй:

- Начальный вход в игровой мир.
- Информацию об измерении.
- Начальную позицию.
- Player Position / Teleport.
- Teleport Acknowledgement.
- Keep Alive.
- Chunk Data.
- Light Data.
- Chunk Visibility.
- Movement.
- Player Spawn/Despawn.
- Пакеты, необходимые для стабильного присутствия клиента в мире.

Критерий готовности: официальный клиент 26.3 может войти на сервер, получить мир и оставаться подключённым.

# 9. ЭТАП 6 — Правильный мультиплеер

Создай систему с авторитетным серверным состоянием.

### PlayerManager

Реализуй:

- Уникальные Session ID.
- Проверенные UUID.
- Player List.
- Подключения и отключения.
- Spawn и Despawn.
- Состояние положения игроков.
- Таблицу видимости.
- Очереди обновлений.
- Очистку ресурсов.

### Player Replication

Когда подключается новый игрок:

1. Создай сессию.
2. Добавь его в Player Registry.
3. Отправь ему информацию о мире.
4. Отправь информацию о других видимых игроках.
5. Уведоми существующих игроков о появлении нового.
6. Синхронизируй движение и повороты.
7. При отключении отправь необходимые удаления сущностей и данных игрока.

Учитывай реальные требования выбранной версии к Player Info, entity spawn, идентификаторам и пакетам синхронизации.

### Тесты

Проверь:

- Два игрока видят друг друга.
- Один игрок двигается, второй видит движение.
- Повороты отображаются корректно.
- Отключение удаляет сущность.
- Повторное подключение не создаёт дубликат.
- Одновременное подключение многих игроков не повреждает состояние.
- Медленный клиент не блокирует остальных.

Критерий готовности: два настоящих Minecraft-клиента могут одновременно находиться в одном мире и видеть друг друга.

# 10. ЭТАП 7 — Поддержка нескольких версий Minecraft

Очень важный этап.

Не пытайся поддерживать разные версии через подмену protocol number.

Разные версии Minecraft могут использовать разные:

- Packet ID.
- Packet Layout.
- Registry Data.
- Entity Metadata.
- Chunk Formats.
- Configuration Protocol.
- Input/Action Formats.

### Целевой порядок

1. Java 26.3 — Protocol 777.
2. Java 26.2 — Protocol 776.
3. Java 26.1.x — Protocol 775.
4. Java 1.21.11 — Protocol 774.
5. Java 1.21.8 — Protocol 772.

Это приоритет исследования, а не обещание, что все версии войдут в первую демонстрацию.

### Versioned Protocol Adapters

Предусмотри интерфейс:

```rust
pub trait ProtocolAdapter {
    fn protocol_version(&self) -> i32;

    fn decode_input(
        &self,
        packet: &[u8]
    ) -> Result<Option<GameInput>, ProtocolError>;
}
```

Это минимальный пример.

В рабочей архитектуре понадобятся также:

- Сериализация серверных пакетов.
- Подготовка Registry Data.
- Версионированное описание сущностей.
- Формирование чанков.
- Configuration State.
- Перевод Minecraft-специфичных действий.

Не разрабатывай один гигантский декодер со множеством условий для всех версий.

Разделяй общие данные и особенности конкретной версии.

### Источники протокола

Используй:

- Minecraft Wiki.
- PrismarineJS minecraft-data.
- Проверенные схемы.
- Данные официального сервера, доступные для законного анализа.
- Пакетные тесты.
- Независимую проверку клиентом.

Если использован генератор packet ID или registry data, зафиксируй его версию, источник входных данных и способ воспроизводимой сборки.

### Compatibility Matrix

Создай:

`docs/COMPATIBILITY.md`

Для каждой версии фиксируй:

- Status.
- Login.
- Online Authentication.
- Configuration.
- World Loading.
- Movement.
- Multiplayer.
- Gameplay Input.
- Rendering.
- Tested/Experimental/Unsupported.

Версия считается поддерживаемой только после тестирования всех обязательных сценариев.

Критерий готовности: как минимум две версии Minecraft работают с одним и тем же серверным игровым состоянием. Остальные добавляются независимо.

# 11. ЭТАП 8 — Minimal Game Runtime

Создай минимальную систему игровых сессий.

Пока не нужно строить сложный SDK.

Реализуй:

- GameSession.
- PlayerContext.
- GameInput.
- GameState.
- GameLoop.
- SessionManager.

### GameInput

Определи абстрактные действия:

```rust
pub enum GameInput {
    Jump,
    PrimaryAction,
    SecondaryAction,
    Move {
        forward: f32,
        sideways: f32,
    },
    SelectSlot(u8),
}
```

Важно: для обычного Minecraft-клиента не все действия доступны как отдельные события клавиатуры. Например, сервер может видеть изменение движения, но не всегда способен однозначно восстановить конкретное нажатие клавиши.

Поэтому адаптер обязан использовать только реально доступные сетевые данные. Для 2D-игр допустимо использовать щелчки, выбор слотов, взаимодействие с предметами и другие обнаруженные надёжные действия.

### GameLoop

Реализуй фиксированную или управляемую частоту симуляции.

Игровая логика не должна непосредственно зависеть от TCP-соединения.

Критерий готовности: сервер способен запустить отдельную игровую сессию и обработать нормализованный ввод игрока.

# 12. ЭТАП 9 — Первый визуальный эксперимент

Нужно доказать, что Voxel Arcade способен показывать игровую информацию обычному клиенту.

### Первоначальный Renderer

Создай простой игровой экран.

Первым вариантом используй минимальную карту Minecraft или другой подтверждённый механизм штатного клиента.

Отобрази:

- Однотонный фон.
- Несколько цветных объектов.
- Движущуюся точку.
- Счётчик.
- Обновление изображения по времени.

Не пытайся сразу реализовать видеостриминг.

### Измерения

Измеряй:

- Размер кадра в памяти.
- Размер сетевых обновлений.
- Отправленные байты в секунду.
- Частоту обновлений.
- CPU на сериализацию.
- RSS процесса.

Сделай возможность ограничивать частоту обновления визуализации.

Например, для эксперимента сравни 5, 10 и 20 обновлений в секунду.

Не гарантируй плавность, пока она не проверена на реальном клиенте.

Критерий готовности: Minecraft-клиент видит изменяющееся изображение без модов.

# 14. ЭТАП 11 — Оптимизация памяти

Основной целевой бюджет — 100 MiB RSS при 20 игроках.

### Необходимые принципы

- Не создавать отдельный процесс на игрока.
- Не создавать отдельный системный поток на каждого игрока.
- Не дублировать статичные чанки.
- Кэшировать сериализованные неизменяемые данные по версии протокола.
- Использовать компактные представления.
- Ограничивать сетевые очереди.
- Освобождать завершённые игровые сессии.
- Минимизировать копирование изображений.
- Использовать общий буфер там, где данные неизменяемы.
- Не загружать ненужные Minecraft-реестры в тяжёлые внутренние объекты.
- Ограничивать размер кэшей.
- Исключать неиспользуемые зависимости из финального бинарника.

Не ухудшай безопасность, корректность и совместимость протокола ради уменьшения RSS.

### Метрики

Собери:

- Idle RSS.
- RSS при 1 игроке.
- RSS при 10 игроках.
- RSS при 20 игроках.
- Пиковый RSS.
- Allocations.
- CPU Usage.
- Network Throughput.
- Количество активных TCP-соединений.
- Размер исходящих очередей.
- Частоту игровых обновлений.

Тестировать после прогрева на Linux Release-сборке.

Желательно иметь результаты повторных прогонов с одинаковыми условиями.

Критерий готовности: получен воспроизводимый отчёт о памяти и производительности с объяснением отклонений от целевого бюджета.

# 19. Первая задача к исполнению

Начни с технического аудита Rust-проектов, поддерживающих Minecraft Java 26.3.

Особенно внимательно исследуй Garnet, Rapidbot, Valence и форматы minecraft-data.

Определи наиболее лёгкий и надёжный путь к реализации собственного сервера без Vanilla-механик.

После выбора зависимостей:

1. Создай Cargo workspace.
2. Реализуй Minecraft Status Ping.
3. Проверь подключение клиента в списке серверов.
4. Реализуй серверный Login.
5. Реализуй online-mode.
6. Реализуй Configuration.
7. Реализуй минимальный Play.
8. Передай клиенту небольшой статичный мир.
9. Проверь движение.
10. Подключи второго игрока.
11. Измерь RSS.
12. После успешного результата приступай к Input Adapter и первому игровому экрану.

**Не начинай с полного Game SDK, сложного рендеринга, Terraria-like и масштабирования на тысячи игроков.**

Первый главный результат — обычный современный Minecraft-клиент стабильно подключается к нашему собственному Rust-серверу и видит другого игрока.

Второй результат — на этом же сервере запускается простая 2D-игра.

Разрабатывай систему так, чтобы версии Minecraft, внутренняя игровая логика и отображение были независимы друг от друга.
